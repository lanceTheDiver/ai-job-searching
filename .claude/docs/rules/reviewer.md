# 代码审查规范

## 审查执行者

**审查必须由与编写代码不同的 agent 执行**，不得由实现者自己审查自己的改动。

- 审查 agent 从全新上下文启动，只拿到被审查的代码（diff、分支或文件路径）和本规范，不得附带实现者的结论、"已验证"之类的说明或预期的审查结果
- 审查 agent 只读，不修改代码；发现的问题交回实现者处理
- Claude Code 中使用子 agent（如 `Agent` 工具的 reviewer 类型）或独立会话；其他工具使用独立的 agent / 会话

## 审查流程

1. **机器检查先行**：实现者先运行 `pnpm format` 格式化，再通过 `pnpm format:check`、`pnpm lint`、`pnpm tsc --noEmit`，不再做人工自查清单
2. **独立审查一次**：审查 agent 按下方审查重点检查，输出审查报告
3. **按严重程度处理**：
   - 有「严重」问题：实现者修复后复审，**最多一轮**；复审后仍有严重问题，交用户决定
   - 只有「中等」「建议」：实现者修改后直接通过，不复审

## 免独立审查

满足以下任一条件可免除独立审查，但需在提交说明或汇报中注明：

- 只改文档或格式
- 改动不超过 50 行，且不涉及 API 接口、安全（认证、密钥、输入校验）、数据存储

## 审查重点

代码审查时应重点关注以下方面：

### Bug 检查

- 逻辑错误
- 边界条件处理
- 空值/undefined 处理
- 错误处理是否完善

### 安全问题

- XSS 跨站脚本攻击
- SQL 注入风险
- 敏感信息泄露（API key, token 等）
- 身份验证和授权问题

### 重复逻辑

- 可以抽象复用的代码
- 相似功能的重复实现
- 应该提取为工具函数的逻辑

### 类型错误

- TypeScript 类型使用不当
- any 类型的滥用
- 类型断言的不当使用
- 缺失的类型定义

### 架构违规

- 不符合项目规范的代码结构
- 违反前端规范（如在组件中直接调用 fetch）
- 不当的依赖关系
- 文件放置位置不正确

### 性能问题

- 不必要的组件重新渲染
- 内存泄漏（未清理的事件监听、定时器等）
- 低效的算法实现
- 过大的打包体积

## 审查原则

1. **仅报告问题，不修改代码**
   - 审查时不直接修改代码
   - 提供清晰的问题描述
   - 给出具体的改进建议

2. **标注严重程度**
   - **严重**：会导致系统崩溃、安全漏洞、数据丢失
   - **中等**：影响功能正确性、代码可维护性
   - **建议**：代码优化、最佳实践改进

3. **提供具体建议**
   - 说明为什么是问题
   - 给出具体的改进方案
   - 提供代码示例（如适用）

## 审查报告格式

```markdown
## 审查结果

### 严重问题

- [问题描述] 位置：文件名:行号
  原因：[说明为什么是问题]
  建议：[如何修复]

### 中等问题

- ...

### 建议改进

- ...
```
